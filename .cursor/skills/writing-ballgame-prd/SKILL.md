# 编写 2026ballgame 项目需求

## 产品基线

除非用户明确修改，所有需求必须遵守：

- 类型：竖屏、轻量、单机跳跃小游戏。
- 首发：微信小游戏；后续适配抖音小游戏；暂不考虑 TikTok。
- 视角：3D 角色与平台，画面强调左、中、右三列判断；优先保证列与落点可读性。
- 核心循环：观察下一平台位置 → 输入左/右方向 → 自动或规则驱动跳跃 → 落地得分 → 继续上升。
- 世界运动：平台环境持续向下移动。
- 失败：方向判断错误、选择空位或未落在平台上时，角色坠落并结束本局；广告复活属于独立规则。
- 难度：随层数提高，平台下坠速度和节奏压力逐渐增加，但必须设可测试的上限并保证至少一条可达路线。
- 强化：开局及第5、10、15关完成后触发三选一强化；已经获得的强化持续生效，后续强化与其叠加，不会替换或作废。效果必须数据驱动、叠加规则明确。
- 第一版：单机玩法、分享、广告、角色与皮肤商城；先实现标准模式第1～20关；不包含排行榜、好友竞争、匹配、实时同步和无限模式。
- 关卡生成：每次只生成即将开始的这一关逻辑数据（层数、路线、果实）；关与关之间停顿，播放 3、2、1、GO 四秒倒计时后再开始跳跃。
- 后续竞争：若实施，使用蓝色小球表现对手，每 10 或 20 层低频同步检查点，不同步完整画面与物理状态。
- 视觉：清新可爱的低多边形 3D 卡通风；角色为第一视觉焦点，目标平台为第二焦点，背景降低饱和度和对比度。
- 商业化：金币、钻石、广告解锁及少量真实付费并存；支付权益以服务端确认结果为准。
- 复活与补救：每个大局最多一次跳跃死亡广告复活和一次分数不足广告直接通关，两种机会独立；跳跃死亡复活后原地继续；分数只在完成整关并落上终点平台后正式结算，分数不足不属于跳跃死亡；广告成功后直接通过当前关，只提交玩家实际得分，不补到保底分。

原始玩法摘要位于 `PRD/跳跃大纲.txt`。涉及核心玩法时先读取它；若与新需求冲突，以用户最新明确决定为准，并同步指出受影响文档。

## 工作流程

1. 读取 `PRD/` 中与本次主题相关的现有文档，避免重复或冲突。
2. 从对话中提取信息并分为：
   - **已确认**：用户明确决定，可写入正式需求。
   - **建议方案**：可写入“设计建议”，不得伪装成已确认需求。
   - **待确认**：会显著影响玩法、成本、排期或实现方式的问题。
3. 若存在 1–2 个会改变方案的关键待确认项，先向用户提问；琐碎事项采用合理默认值并标注。
4. 明确本次需求属于哪个版本：
   - V1：微信单机首版。
   - V2：运营、云存档、排行榜或好友挑战。
   - V3：低频同步影子竞赛。
5. 编写或更新 PRD，并给出可验证的验收标准。
6. 完成后检查术语、版本范围、边界条件、异常流程和文档冲突。

## 文档规则

- 所有正式需求保存在 `PRD/`，使用 Markdown，编码 UTF-8。
- 文件名使用中文主题，例如：
  - `PRD/核心玩法.md`
  - `PRD/三选一强化系统.md`
  - `PRD/商城与货币.md`
  - `PRD/广告复活.md`
  - `PRD/主界面.md`
- 一个文档聚焦一个可独立评审的系统；不要把整个游戏塞进单一超长文档。
- 文档开头写明状态、目标版本、负责人和最近更新日期。
- 使用稳定编号，便于讨论和验收，例如 `GAME-JUMP-001`。
- 使用“必须 / 应该 / 可以”区分强制、推荐和可选项。
- 数值尚未验证时写“初始建议值”，并说明验证方式，不写成最终值。
- 不使用“等等”“类似这样”“做得好看”等不可验收表述。
- 不把 UI 稿、3D 美术稿、程序实现方式混成同一交付；需求可说明依赖关系。
- 未获授权时，不在对外需求中使用“英雄联盟”“海克斯”等品牌名称；统一使用“强化”或项目原创名称。

## 玩法需求专项检查

涉及跳跃、平台、路线、速度或死亡时，必须写清：

- 操作方式：左/右输入如何映射到三列。
- 起跳触发：自动、点击、蓄力或其他规则。
- 可跨列范围：相邻列还是允许跨两列。
- 平台生成：可达性验证、预告距离和连续极端路线限制。
- 落地判定：碰撞区域、容错、Good、Perfect。
- 下坠速度：基础速度、增长曲线、上限、强化倍率。
- 反应时间：各速度阶段必须留给玩家的最短判断时间。
- 死亡：触发条件、表现、复活和结算。
- 公平性：不得因透视、遮挡、帧率或未进入可视范围造成不可避免死亡。
- 暂停与恢复：切后台、广告播放后恢复时的状态。

## 商业化需求专项检查

涉及广告、货币、商城或支付时，必须写清：

- 获取、消耗和库存变更。
- 金币、钻石、广告和人民币商品的边界。
- 支付取消、失败、超时、重复回调和补单。
- 广告未加载、播放中断和奖励发放条件。
- 客户端只负责展示；真实支付权益由服务端验签并幂等发放。
- 不用付费或广告制造无法继续游戏的强制障碍。

## 验收标准写法

优先使用 Given / When / Then：

```markdown
- Given 玩家位于中列且左列为唯一可达平台
  When 玩家在有效输入窗口内选择左侧
  Then 角色落到左列平台，增加层数与分数，本局继续

- Given 激励广告未完整播放
  When 平台返回关闭或失败
  Then 不消耗复活机会、不发放复活奖励，并允许玩家进入结算
```

验收标准必须可由策划、开发或测试明确判断通过/失败。

## 更新现有 PRD

- 保留原文档中仍有效的需求编号。
- 不静默覆盖产品决定；在“变更记录”说明修改原因和影响范围。
- 若新决定影响其他 PRD，列出需要同步更新的文件。
- 用户只要求讨论或建议时，不直接修改正式 PRD；用户要求“写入、更新、生成文档”时再落盘。

## 输出前检查

- [ ] 文档位于 `PRD/`
- [ ] 已区分已确认、建议和待确认
- [ ] 已说明本期包含与不包含
- [ ] 核心规则不存在自相矛盾
- [ ] 所有关键状态和失败路径有定义
- [ ] 数值标注为最终值或初始建议值
- [ ] 验收标准可执行
- [ ] 未擅自扩展到后续版本
- [ ] 未使用未授权品牌词作为正式名称
